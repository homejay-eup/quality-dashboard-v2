# /brainstorming — 開案設計對話

> 在寫任何代碼前，透過結構化對話把「模糊的想法」轉化為「清晰的設計文件」。

## 觸發時機

- 新功能開案，想法還模糊
- 涉及多系統交互，需要釐清邊界
- 想讓 Claude 真正理解「為什麼」，而非只執行「做什麼」

## 執行流程

**Step 1：理解現有脈絡**
先讀取以下檔案，理解現有架構與技術棧：
- `_管理/常駐/專案規格.md`（技術棧 STACK_RULES）
- `_管理/常駐/方案紀錄.md`（過往決策）
- `_管理/常駐/領域詞彙.md`（本專案專屬用語——**對話中一律使用此處的詞**）
- 相關 `_管理/specs/` 規格（若有）

**Step 2：蘇格拉底式提問**

### 提問紀律（強制，四條）

1. **一次只問一個問題**，等回答後再問下一個。**絕不一次丟多個問題**——一次問多題會讓人一頭霧水、答案品質下降。
2. **每個問題都附上「建議答案」**並說明理由，不要空白提問。使用者可以直接採用、選別的、或補充說明。
3. **能自己查的不要問**：先用工具（讀檔／CodeGraph／Grep／web）研究事實性細節，**只把「需要使用者決定」的事拿來問**。不確定該不該問時的判準——「這題的答案存在於程式碼或文件裡嗎？」是 → 自己去查。
4. **沿決策樹逐一往下**：先問會影響後續分支的決策，解決決策之間的依賴，不跳著問。

### 問題維度涵蓋

**A. 細化你已經想到的事**
- **目標**：這個功能解決什麼問題？對誰？
- **範圍**：最小可行版本是什麼？哪些不在這次範圍？
- **技術邊界**：前端/後端/DB 各自的職責？
- **備援**：失敗情境怎麼處理？
- **相依**：會影響哪些現有功能？
- **產出物落點**（STACK_RULES 未涵蓋時才問）：會產生程式碼以外的產出物嗎（腳本／匯出檔／報告）？放哪、命名、改版怎麼處理？

**B. 挖掘你還沒想到的事（強制，至少問 2 題）**

上面五個維度都是「已知事項的細化」，這組是逼出**盲點**——**不問這組，等於只驗證了你原本的想法**：

- **誤用**：這功能上線後，使用者最可能怎麼**誤用**它？（誤用比故意破壞常見得多）
- **未驗證假設**：有哪個我們現在當成理所當然、但其實**沒驗證過**的假設？
- **未來擋路**：如果三個月後要擴充，現在哪個決定**會擋路**？
- **空狀態與極端值**：完全沒資料時畫面長什麼樣？資料量變 100 倍時呢？
- **半途中斷**：使用者做到一半離開／斷網／重複送出，會發生什麼？

### 終止條件
達成**共識**為止（不是「問完清單」）。**在使用者確認共識達成前，不得開始任何實作**。

**Step 3：探索替代方案**
針對核心技術選擇，依 `CLAUDE.md`「決策分級判準」判斷：
- **偏離推薦棧或使用者有疑慮** → 依 `_管理/SOP/技術選型呈現.md` 三層格式呈現（完整比較表→關鍵差異→AI建議），等待使用者確認
- **採用推薦棧／純內部實作手法** → AI 自主選定，記錄於 `方案紀錄.md`，不停下確認

**Step 4：產出設計文件**
對話結束後，整理為設計文件，格式如下：

```markdown
# 設計文件：[功能名稱]

## 功能目標
（一句話說清楚）

## 你會看到什麼（白話，給非技術者對焦）
（用「你／使用者」視角，2–4 句，不出現檔名／型別／API／資料庫等詞。
 下一步的功能規格 `{功能名}.md` 頂端會沿用這段。）

## 範圍界定
- 本次包含：
- 本次不包含：

## 技術方案
（確認的實作方式）

## 主要流程
（步驟或流程圖）

## 邊界條件與備援
（失敗情境、邊界值）

## 相依影響
（可能連帶影響的功能）

## 驗收標準
（散文式描述即可；下一步會轉成功能規格 `{功能名}.md` 的可逐條勾選條件，**那份才是 tester 的驗收依據**）
```

**Step 5：設計文件送審（第二雙眼睛，強制）**

設計文件**不可由產出它的同一個 session 自我審查**——提問時漏掉的，自己回頭看也一樣看不到。

派 `reviewer`（唯讀，適合此任務）讀設計文件，**只審文件、不看程式碼**，回報四件事：

```
1. 哪裡還模糊？（子 Agent 拿到會需要猜的地方）
2. 哪個情境沒有定義？（錯誤／空狀態／中斷／極端值）
3. 驗收標準能不能真的驗？（有沒有「體驗要好」這種無法驗證的條目）
4. 有沒有自我矛盾？（前面說 A、後面假設非 A）
```

reviewer 回報後，主 Agent 就發現的缺口**回頭補問**（仍守一次一問紀律），補完再更新設計文件。

**Step 6：等待確認**
設計文件（含送審後的補正）完成後，等待你確認「可以開始實作了」，才進入執行階段。

## 注意

- 整個 brainstorming 過程在主 session 執行，**不委派子 Agent**（例外：Step 5 派 reviewer 審文件）
- **設計文件存 `_管理/specs/{功能名稱}-設計.md`**（⚠️ 不要存成 `{功能名稱}.md`——那是**功能規格**，格式不同、給 tester 逐條驗收用）
- **設計文件確認後，接著產出功能規格 `_管理/specs/{功能名稱}.md`**（格式見 `_管理/範本/功能規格範本.md`）：把設計文件的「你會看到什麼」段落原樣帶到規格檔頂端、驗收標準轉成**可逐條勾選的驗收條件**，再補欄位定義、頁面／元件清單、對應測試腳本路徑（開發區塊）
  > 兩份文件的分工：**設計文件＝為什麼與要做什麼**（決策脈絡）／**功能規格＝具體規格與怎麼驗**（tester 的依據）
- 若腦力激盪結果改變了技術選型，同步更新 `_管理/常駐/方案紀錄.md`
- **對話中出現「需要解釋兩次以上的概念」→ 收斂成一個詞，補進 `_管理/常駐/領域詞彙.md`**（一個詞取代一段解釋，之後溝通更精準也更省 context）
- 若本次結果判定為**大任務**（**觸發條件見 `CLAUDE.md`「Context 預算規則」表——唯一判斷來源，此處不重述數字**），接著用 `_管理/範本/任務分解範本.md` 拆成**垂直切片**子任務（每片可獨立驗收）
