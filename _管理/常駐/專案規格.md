## 產品概述

- 產品名稱：設備品質分析儀表板 v2
- 核心功能一句話描述：把設備的派工／維修／報廢／回廠資料彙整成品質指標，並產生給主管看的落地頁報告；純前端直接讀 Google Sheet，即時彙整、免上傳
- 目標使用者：內部品管／採購同事與主管，透過瀏覽器開網址直接看
- 最在意的面向：數字正確（程式要跟 `計算規則.md` 一致）、資料來源鮮度（即時讀取 vs 需要快照才能跨期比較）

## 分工

| 誰 | 負責 | 檔案 |
|---|---|---|
| homejay | 品質工具：資料完整與正確、計算規則、儀表板畫面 | `js/` 中除了報告以外的檔案、`css/style.css`、`index.html`、`_管理/常駐/計算規則.md`、`scripts/`、`apps-script/` |
| lala（lala@eup.com.tw）| 落地頁報告的呈現 | `js/report_v3.js`（正式報告）、`js/report.js` 的報告產生部分 |

- `js/report.js` 裡的快照匯出／解析（`buildBundle`、`exportSnapshot`、`parseSnapshot` 等）是品質工具在用的，但檔案在 lala 那邊，要動先講。
- 報告直接用品質工具的計算結果：`App.transform.buildDetail` 的明細欄位、`App.metrics` 的 `computeKPI`／`aggregate`／`applyFilter`／`computeOnlineAge`、`App.app` 的 `dataForDevice` 與 `state`。改這些的輸出欄位或參數會影響報告。

## 技術架構

- 前端 Web：純前端（`index.html` / `css/` / `js/`），**無框架、無打包器**，瀏覽器直接讀 Google Sheet 的 gviz CSV 即時彙整
- 資料來源：見 `計算規則.md`「資料來源」
- 雲端輔助服務：Google Apps Script（`apps-script/Code.gs`）——把快照與報告寫進共用 Drive、列出歷史快照供跨期比較，部署方式見 `apps-script/README.md`
- 部署平台：GitHub Pages，直接發布 `master` 分支根目錄（無 build、無 GitHub Actions，push 到 master 即上線 https://homejay-eup.github.io/quality-dashboard-v2/ ）
- 認證：Google 登入閘（限 `@eup.com.tw` 網域，`js/auth.js`，一次授權含讀私有 Sheet）
- 選型原因摘要：純前端＋直讀 Sheet＝免上傳，是這個專案存在的核心目的；GitHub Pages 免另建伺服器
- 排除選項：正式後端服務——沒有寫入正式資料庫的需求，靜態頁面已足夠

## 專案結構

```
專案根目錄/
├── index.html / css/ / js/   ← 網站本體（直接部署）
│   └── js/data/purchase_dates.json ← 條碼→最舊進貨日（由 scripts/ 產生，要進版控）
├── apps-script/              ← 雲端快照接收端（Google Apps Script）
├── scripts/                  ← build_purchase_dates.py：從「產品進貨單」條碼 Excel 產生 purchase_dates.json
├── _開發檔案/                 ← 健康檢查（scripts/）與 node 單元測試（tests/e2e/*.spec.ts，內容為純 JS）
├── _產出/                     ← 非程式碼成品
├── _管理/常駐/                ← 常駐檔（含 計算規則.md）
├── _管理/specs/               ← 功能規格與設計紀錄
└── package.json              ← 只提供 `npm test`，無套件依賴
```

## 規範與約定

- 命名：管理文件用中文檔名；`js/`、`css/`、`scripts/`、`apps-script/` 維持英文小寫

- **程式碼目錄**：前端邏輯依關注點拆檔於 `js/`（`transform.js` 清洗與分類規則、`metrics.js` 指標與彙整、`filters.js` 篩選、`detail.js`／`rawtable.js`／`tablefilter.js` 表格、`sheets.js` 讀 Google Sheet、`auth.js` 登入、`cloud.js` 雲端快照、`report_v3.js` 落地頁報告）；不集中成單一大檔

- **開發指令**：無 build／型別檢查；**驗證＝`npm test`**（健康檢查：每個 js 檔語法＋id 存在＋核心函式還在；再跑 node 單元測試）；本機預覽用靜態伺服器（如 `python -m http.server`）；改了 `js/`、`css/` 檔要把 `index.html` 對應的 `?v=` 版號加一；**新的 `.spec.ts` 必須能用 node 直接跑（純 JS），並加進 `package.json` 的 test 指令**；需要瀏覽器的驗收用 Python 版 Playwright（見 `踩坑記錄.md` M-9）
- **協作**：兩個人都會推送到 `master`，開工前先 `git pull`
- **部署**：push 到 `master` 即上線，屬紅線第 4 項，每次 push 前先問使用者（見 `CLAUDE.md`）
- **禁區**：`apps-script/Code.gs` 的 `FOLDER_ID` 是使用者個人 Drive 資料夾 ID，不可提交明文（部署細節見 `apps-script/README.md`）；報告檔案見上方「分工」

## 型別契約聲明（高危介面登記表）

| 檔案 / 型別 | 說明 | 危險等級 |
|---|---|---|
| `js/data/purchase_dates.json` | 條碼→最舊進貨日，規則 E 的進貨日優先讀這份；格式改變會影響回廠年限 | 高 |
| `App.transform.buildDetail` 回傳的明細欄位、`App.metrics.computeKPI`／`aggregate` 的回傳欄位 | 儀表板三張表、KPI 卡與 lala 的落地頁報告都直接讀；改名或改意思要同步所有使用處並告知 lala | 高 |
| 快照 bundle 結構（`js/report.js` 的 `buildBundle`）| 已存在雲端的舊快照要能繼續載入，跨期比較才不會壞 | 高 |
