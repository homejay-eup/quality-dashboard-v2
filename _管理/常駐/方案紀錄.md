# 方案紀錄 — 已定案決策 + 討論脈絡

> 本檔是「本專案做過哪些決定、為什麼」的**單一來源**。
> git log 記「做了什麼」，這裡記「為什麼這樣規劃」；兩者互補，不重複。

**兩個區塊，各有用途：**

| 區塊 | 是什麼 | 誰讀 | 寫入規則 |
|---|---|---|---|
| **一、已定案決策速查表**（下方）| 結論的一行速查——技術選型、schema、UI 規範、部署、其他架構決策 | 子 Agent 開工前掃一遍，確認實作方向不違反已定案；主 Agent 啟動時讀 | 追加列；決策被取代時只改「狀態」欄（`生效` → `已被 #N 取代`），不刪列 |
| **二、討論脈絡**（速查表之後）| 每個決策的完整背景：考慮過的選項、為何選它、排除原因、影響範圍 | 主 Agent 需要回顧「當初為什麼」時按需讀 | 只追加，不修改既有條目 |

> 一個決策**兩區塊各記一次**：速查表一行（結論），脈絡區一則（原因）。速查表的「脈絡」欄指向脈絡區的日期標題。

## 二、討論脈絡

> 格式：`### [YYYY-MM-DD] {討論主題}`，每則含：
> - **討論背景**：為什麼要討論這個
> - **考慮的選項**：列出評估過的方案
> - **決策結果**：選擇了什麼、原因是什麼
> - **排除原因**：其他選項為何不採用
> - **影響範圍**：哪些功能或後續步驟需要配合這個決策

### [2026-09-18] 專案搬家與範本套用

- **討論背景**：原「品質分析」AI-OS 專案資料夾內容雜亂（其實走成了另一個 CRM 資料查詢工具），使用者想捨棄，改用既有的 GitHub repo `quality-dashboard-v2`（設備品質分析儀表板 v2）作為新的工作資料夾，並沿用 AI-OS 範本流程繼續開發。
- **考慮的選項**：
  1. 把新 repo clone 進舊的「品質分析」資料夾內部（巢狀 git）
  2. 直接在本機既有的 `品質分析\` 或 `品質分析\新版儀表板\` 資料夾上繼續工作
  3. 在 Desktop 開獨立新資料夾，從 GitHub 重新 clone `master`，另外把本機唯一持有的規則文件／腳本補進來
- **決策結果**：採用選項 3。原因：查證發現本機兩份既有 clone（`品質分析\` 落後 60 commit、`品質分析\新版儀表板\` 落後 50 commit）都缺少已上線的 Google 登入閘、`report.js` 大改版等功能，若以本機為準會讓網站與程式碼倒退；GitHub `master` 分支是 GitHub Pages 實際部署來源（legacy branch 部署、無 build 步驟），以它為準才能保證程式碼與線上成品一致。
- **排除原因**：選項 1 造成巢狀 git、外層 repo 追蹤不到內層變更，且把新專案埋進正要丟棄的雜亂資料夾；選項 2 會延續程式碼落後、且該資料夾同時混雜三個不同血緣的專案（quality-dashboard-v2 兩份 clone + 另一個完全不同的 GitHub repo `quality-analysis`）。
- **影響範圍**：後續 `_管理/常駐/` 四檔改以本專案（設備品質分析儀表板）為主體重新撰寫，不沿用舊「品質分析」資料夾（CRM 資料工作站）的業務內容；`.claude/agents`、`.claude/skills`、`_管理/範本`、`_管理/SOP`、`CLAUDE.md`、`README_範本使用說明.md`、`.mcp.json` 等範本骨架原樣複製過來，`.claude/memory` 不帶（重新累積）。

### [2026-09-18] 規則文件補進版控

- **討論背景**：`設備品質分析_分冊文件/00_規則定義.md`（彙整邏輯唯一來源，目前 v9）與 `新版產出/build_分析總表.py`（Python 批次腳本）從建立以來只存在使用者本機的 `品質分析\` 資料夾，從未 commit 進任何 git repo，也不在 GitHub `quality-dashboard-v2` 裡，沒有版本歷史、沒有備份。
- **考慮的選項**：①維持只放本機 ②補進 `quality-dashboard-v2` repo 版控
- **決策結果**：採用②，隨搬家一併 commit 進新資料夾所在的 repo，讓這份「唯一邏輯來源」終於有 git 歷史可查。搬入時排除 `新版產出/` 下 3 個各 9–10MB 的 `.xlsx` 快照與 `__pycache__`（產出物/快取，非邏輯本體，不需要版控）。
- **排除原因**：無（風險是「本機唯一備份」，補版控沒有明顯壞處）。
- **影響範圍**：`repo README.md` 目前寫「規則 A–F（v5）」，與規則文件實際版本（v9）不一致，屬單檔文件小修正，待後續處理；改動彙整邏輯前，兩條產出路徑（Python／前端 JS）都要同步檢查是否也要更新 `00_規則定義.md` 版本號。

### [2026-09-18] 摘錄資料來源核對記錄

- **討論背景**：搬家過程中發現使用者另一個獨立專案 `Web App for Develop - AI OS_DB_範本\`（EUPCRM 資料工作站，跟 `品質分析\` 是同一個 CRM 專案的分岔複本，多 2 個 commit）在 2026-09-18 做過一次「本專案讀取的 Google Sheet 資料來源 vs EUPCRM BI 資料庫」交叉核對，解出 `SQL回廠時間`／`SQL_派工`／`SQL_維修` 三個分頁對應的資料表與精確篩選 SQL、可信度分級，以及 `SQL_報廢`／`SQL上線量` 兩個尚未解開的缺口。使用者認為這些內容未來可能跟本專案有關，要求現在就搬過來參考。
- **考慮的選項**：①整個 `_管理/db_mapping/`（56+ 份文件，含大量跟本專案無關的 CRM UI 畫面對照）都搬過來 ②只摘錄跟本專案資料來源直接相關的核對結果，寫成獨立參考文件
- **決策結果**：採用②，新建 `_管理/specs/資料來源核對-BI資料庫比對.md`，內容摘自該專案 commit `5b50dff`／`e139c1e` 的 `db_mapping/回廠時間.md`／`派工一覽表.md`／`維修總表.md`／`報廢作業.md` 與踩坑記錄 Q-11~Q-15，包含各分頁核對結果表、兩條已解出的精確篩選 SQL、核對方法論五點、尚未解決的缺口清單。
- **排除原因**：選項① 的 `db_mapping/` 絕大多數內容是 EUPCRM.exe 各 UI 畫面（客戶服務、工單、庫存查詢等）的欄位對照，跟本專案（純讀 Google Sheet 的靜態儀表板）完全無關，整搬會違背搬家時「乾淨、不混入其他業務領域」的原則。
- **影響範圍**：本文件是**參考資料**，不是本專案的功能規格（tester 不依此驗收）；之後若要評估「改成直接查 BI 資料庫取代 Google Sheet」或想解開 `SQL_報廢`／`SQL上線量` 的缺口，可從這份文件的方法論與已知缺口清單接續，不必重新從零核對。

### [2026-09-18] 在線平均已使用年限

- **討論背景**：使用者要求新增「總線上量」的平均已使用年限指標，並提供一份新的 Google Sheet「車機鏡頭上線明細」（逐條碼進貨日/安裝日）當資料來源。查證發現該表**需要登入才能檢視**（gviz 端點回 `access_denied`），跟現有公開來源表不同；且裡面多了「客代」「客戶名稱」等現有表沒有的個資欄位。
- **考慮的選項**：①請人另建一份不含客戶欄位的乾淨版分頁，設成公開連結 ②直接把整份表（含客戶欄位）設成公開連結 ③改用現有 Google 登入的 OAuth 授權去讀 Sheets API，Sheet 分享設定維持不變
- **決策結果**：採用③。使用者評估後認為，比起改動 Sheet 分享設定或請人額外維護一份乾淨版，寧可多花一點工程成本在前端加 OAuth 授權流程，讓客戶資料維持原本「需登入才能看」的保護，不因為這個新功能而擴大暴露面。已確認可以做到「只有第一次多一次同意畫面，之後背景靜默換發授權」，不影響既有登入體驗。
- **排除原因**：選項①③都需要修改 Sheet 本身的分享設定或另外維護一份資料，選項①③也都會讓知道連結的任何人（不只登入本站的人）看到客戶名稱，使用者認為這個暴露面不必要，寧可技術上多做一點事換取資料維持原有保護層級。
- **影響範圍**：`js/auth.js` 需新增 OAuth token client 邏輯；`js/sheets.js`／`js/metrics.js` 需新增對應讀取與計算函式；`js/cloud.js`＋`apps-script/Code.gs` 的既有「匯出本期快照」需擴充納入這份資料；`00_規則定義.md` 需新增規則 H。已查證此表的設備範圍（總筆數 220,849）與公開來源表「SQL_上線量」分頁車機+鏡頭加總完全一致，不需處理範圍對不齊的問題。完整設計脈絡見 `_管理/specs/在線平均已使用年限-設計.md`。
