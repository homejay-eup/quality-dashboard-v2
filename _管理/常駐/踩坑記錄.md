## 專案搬家與環境

**M-1：使用者電腦上同一個 GitHub repo 可能同時有多份本機 clone，且彼此落後進度不同**
- 根因：`C:\Users\EupUser\Desktop\品質分析\`（根目錄）與其內部巢狀的 `新版儀表板\` 都是 `quality-dashboard-v2` 的獨立 clone，分別落後 GitHub `master` 60 個、50 個 commit；根目錄還有 2 個未 commit 的修改（`css/style.css`／`js/filters.js`），比對後確認是登入功能上線前的舊字級調整，已被後續 commit 覆蓋，不是遺失的工作。
- 修法：要判斷「哪份是最新的」，不能只看本機檔案時間，要 `git fetch` + `git log HEAD..origin/master` 實際比對 commit 數，並用 `git diff HEAD origin/master -- <檔案>` 確認未 commit 的修改是否已被上游覆蓋。以 GitHub `origin/master` 為準，因為它才是 GitHub Pages 實際部署的內容。

**M-2：業務邏輯的「唯一定義文件」可能從未進版控，只存在使用者本機**
- 根因：`設備品質分析_分冊文件/00_規則定義.md`（規則 A–F）與對應的 Python 批次腳本 `新版產出/build_分析總表.py` 建立以來只放在本機資料夾，未被任何 git repo 追蹤；使用者自己記憶的版本號（v5）跟文件實際版本（v9）也有落差，代表這份文件本身也可能隨時間漂移而使用者未必記得最新狀態。
- 修法：開新 session 討論這個專案的彙整邏輯前，先讀 `00_規則定義.md` 的版本號 header，不要憑使用者口述或先前記憶假設版本；文件內容已於 2026-09-18 隨搬家補進本 repo 版控（見 `方案紀錄.md`），之後改規則要記得同步更新 Python 腳本裡的 `RULE_DOC_VERSION` 字串。

**M-3：`repo README.md` 記載的規則版本號跟規則文件實際版本不同步**
- 根因：`README.md` 寫「規則 A–F（v5）」，但 `設備品質分析_分冊文件/00_規則定義.md` 實際已到 v9（2026-07-29 更新），文件更新時沒有回頭同步 README。
- 修法：改動彙整邏輯、更新規則文件版本號時，順手檢查 `README.md` 有沒有提到版本號，一併更新，避免文件互相矛盾。

## 多任務並行委派與 Git

**M-4：多個子 Agent 並行執行、各自 `git add` 完自己的檔案後，主 Agent 若 `git commit` 沒限定路徑，會把所有人 staged 的東西一起提交**
- 根因：本專案規則是「子 Agent 只 `git add`、不 commit；主 Agent 兩關（tester+reviewer）都過才 commit」。但當兩個獨立任務平行委派、都已完成 `git add`，若主 Agent 這時單純想 commit「自己順手改的一個小文件」而執行 `git commit -m "..."`（沒有帶路徑），Git 會把**當前整個 index**（含另外兩個任務已 stage、但還沒走完 tester/reviewer 驗證的程式碼）一起打包進這個 commit——commit 訊息因此跟實際內容不符，而且違反「兩關都過才 commit」的把關順序（本 session 2026-09-18 實際發生過一次，好在後續補做的驗證都通過，沒有造成損失）。
- 修法：多任務並行時，`git add` 要用明確檔案清單（不要 `git add -A`，本專案已有這條規則），**`git commit` 前一定要先 `git status`／`git diff --cached --name-only` 確認 index 裡只有這次真的要進的檔案**；如果發現 index 混了別的任務的東西，先 `git reset <不該進的檔案>` 把它們移出 staging 再 commit，不要直接對整個 index 下 `git commit`。

## 部署（GitHub Pages）

**M-5：GitHub Pages（legacy／Jekyll 組裝模式）建置卡住不動，`git push` 上去也不會反映在線上網站，且沒有明確錯誤訊息**
- 根因：2026-09-18 搬家時新增了一個 21MB 的 `js/data/purchase_dates.json`（前端查進貨日要用，屬必要檔案，不能拿掉）。查 `gh api repos/<owner>/<repo>/pages/builds/latest` 發現，自那之後 GitHub Pages 就一直卡在 `"status":"building"`、`duration` 停在 0 不動，`error.message` 是 `null`（沒有可讀錯誤訊息）；上一次真正成功的建置（`status:"built"`）是搬家前、8/6 的舊版內容。本專案是純靜態頁（無 build 步驟），但 repo 根目錄一直沒有 `.nojekyll`，GitHub Pages 預設會跑 Jekyll 組裝，推測是這層不必要的組裝在處理大檔案時卡住/逾時，導致往後所有 push（包含整個「在線平均已使用年限」功能）雖然都成功進了 `origin/master`，卻從未真正發布到線上——**只看 `git log`／`git push` 有沒有成功不能判斷網站有沒有更新，兩者是分開的系統**。
- 修法：在 repo 根目錄加一個空的 `.nojekyll` 檔（告訴 GitHub Pages 跳過 Jekyll、直接發布原始檔案），push 後用 `gh api repos/<owner>/<repo>/pages/builds/latest` 確認新的 build 是否變成 `"status":"built"`（本次跑了約 57 秒後成功）。以後任何「push 了但網站沒變」的情況，第一步先查這個 API，不要預設是瀏覽器快取問題。
- **附帶發現（尚未處理，需使用者決定）**：查的過程中發現這個 GitHub repo 本身是**公開**（`public repo`，不只是 Pages 網站公開），代表 `_管理/` 底下的內部決策文件、規則文件等，現在就已經能透過 GitHub 網頁直接被任何人看到，跟前端的 Google 登入閘（那只擋得住網頁應用程式本身）無關。加了 `.nojekyll` 後這些文件多一條「透過網站網址也翻得到」的路徑，但本質風險不算新增（repo 本來就整個公開）。要不要把 repo 改成不公開，留給使用者決定。

## 驗證方法（本機/瀏覽器自動化）

**M-6：AI 沒辦法自動化跑完「登入 Google」這一步，涉及登入才能看到畫面的功能，驗證只能到「程式碼邏輯層」為止**
- 根因：`js/auth.js` 的登入按鈕（ID Token）與「重試」按鈕背後的 Sheets 授權（OAuth token），瀏覽器都要求「真人點擊手勢」才會讓 Google 的登入彈窗/FedCM 正常跳出——透過瀏覽器自動化工具（不管是 Claude 內建瀏覽器還是 Claude in Chrome 擴充功能）送出的合成點擊事件，Chrome 都不當成合法手勢：手動實測會直接卡在「loading」狀態、Google 端 callback 完全不會被呼叫，也不會有任何主控台錯誤訊息可查（等同無限等待）。
- 修法：這類功能沒辦法用自動化工具跑完整個「登入→看畫面」的驗收流程，只能做到：①`node -c` 語法檢查 ②本機靜態伺服器確認頁面載入、主控台無新增錯誤（不需要登入這步就能檢查的範圍）③程式碼邏輯逐行核對（資料從哪來、guard 條件對不對、有沒有複製到既有已測試過的邏輯）。真正「登入後畫面長怎樣」這一段，要請使用者自己登入操作後確認，如實跟使用者說明這個限制，不要宣稱有看到畫面渲染結果。
- 例外：如果使用者本來就已經在某個瀏覽器分頁保持登入狀態（例如透過 Claude in Chrome 連到使用者已登入的正式網站），AI 可以在那個已登入的分頁上用 `javascript_tool` 直接呼叫 `App.metrics`/`App.app.state` 等現有函式核對計算結果（不需要重新觸發登入），但這只能驗證「已經部署上線」的程式碼，驗證不到「本機還沒 push 的新改動」。
