# 任務分解範本

> ⚠️ **本檔是空白格式範本，不要直接填在這裡**。複製此格式，填好的內容存到 `_管理/任務分解.md`（實例）。
> 大型任務使用此格式（**觸發條件見 `CLAUDE.md`「Context 預算規則」——唯一判斷來源**；執行流程見 `_管理/SOP/大型任務.md`）。
> 由主 Agent 在 Session A（分解 session）產出，執行 session 每次只讀此檔取得當前子任務。

---

## 切片原則（分解前必讀）

**每個子任務必須是「垂直切片」，不是「水平切片」。**

垂直切片＝切一條**窄但完整**穿過所有層的路徑（資料層→邏輯層→介面層→測試），完成後**可獨立驗收或操作**。

```
❌ 水平切片（禁用）：
   子任務1 做完所有資料表       → 看不到任何東西
   子任務2 做完所有 API         → 還是看不到
   子任務3 做完所有畫面         → 到這裡才第一次能驗收

✅ 垂直切片（必用）：
   子任務1「使用者能新增一筆 X」→ 表 + API + 畫面 + 測試，只做這一條 → 現在就能點開驗收
   子任務2「使用者能編輯 X」    → 同樣完整一條
```

**判斷標準**：每個子任務完成後，**使用者（含看不懂程式碼的人）能自己點開來確認它成立**。若無法，切片方式錯了，重切。

> 一個垂直切片同時要資料層和介面層時，仍是一次派工一角色：拆兩次派工（先 `data` 定資料存取與介面 → 再 `frontend` 接），或由主要落點角色主導、另一層以最小改動帶過。

**大小上限**：一個子任務要能塞進單一 session 的 context（對應 CLAUDE.md「修改或新增 > 5 檔就再拆」規則）。

---

## 顆粒度原則：垂直切片 × 小步驟（兩個不同維度）

| 維度 | 管什麼 | 判準 |
|---|---|---|
| **垂直切片**（上一節）| **完整性** — 每片穿透所有層 | 使用者能自己點開驗收 |
| **小步驟**（本節）| **顆粒度** — 每步小到不會出錯 | 一個步驟＝一個 2–5 分鐘動作 |

**理想的步驟節奏**（一個子任務內部）：
```
寫測試 → 確認測試失敗（紅）→ 實作 → 確認測試通過（綠）→ git add
```
> ⚠️ **子任務不自行 commit**——`git add` 後由主 Agent 在 tester＋reviewer 兩關通過後統一 commit（見 `CLAUDE.md`「commit 責任分工」）。
每一步都是 2–5 分鐘可完成的單一動作，**不要出現「幾小時的大包」**。

---

## 🚫 無抽象規則（強制）

**寫任務規格時禁止佔位語言。出現以下字樣代表這份分解沒寫完，不可拿去派工：**

| 禁用寫法 | 該寫成 |
|---|---|
| 「TBD」「待補」「之後決定」 | 現在就決定，不確定就先問使用者 |
| 「加上驗證」 | 驗證什麼欄位、什麼規則、失敗顯示什麼訊息 |
| 「跟任務 3 類似」 | 完整寫出來（讀計畫的是 fresh context 的子 Agent，它看不到任務 3）|
| 「處理錯誤情境」 | 列出哪些錯誤情境、各自怎麼處理 |
| 「更新相關檔案」 | 明列確切檔案路徑 |

**每個任務必須具體到**：確切檔案路徑、要用的指令（可直接複製執行）、預期輸出。

> **為什麼這麼嚴**：每個任務都派給**fresh context 的子 Agent**（見 CLAUDE.md「派工顆粒度」），它沒有你的對話記憶——寫得模糊它只能猜，猜錯就是返工。**寫給不認識這個專案的人看**是正確的心態。

---

### 例外：大範圍機械式改動走 expand-contract

改名／改介面／換寫法這類**橫跨大量呼叫點**的機械式改動，無法垂直切片，改用三階段：

| 階段 | 做什麼 | Blocked by |
|---|---|---|
| Expand | 新形式與舊形式**並存**（不刪舊的，不改呼叫點）| 無 |
| Migrate（可多批）| 分批把呼叫點改成新形式，每批獨立可驗 | Expand |
| Contract | 移除舊形式 | **所有** Migrate 批次 |

好處：任何一個階段做完系統都還能跑，不會卡在「改一半」的破碎狀態。

## 子任務清單

| # | 子任務名稱 | 本票交付什麼（使用者可見） | 負責 Agent | Blocked by | 狀態 | Commit |
|---|---|---|---|---|---|---|
| 1 | | | frontend / data / tester | 無 — 可立即開始 | 待執行 | — |
| 2 | | | | 子任務 1 | 待執行 | — |
| 3 | | | | 無 — 可立即開始 | 待執行 | — |

> **`Blocked by` 欄的兩個用途**：
> 1. 決定執行順序（被阻擋的不能先做）
> 2. **判斷可否平行**：標「無 — 可立即開始」的子任務彼此**才可以**開兩個 session 平行做（worktree 隔離做法見 `SOP/大型任務.md`）；有阻擋關係的必須序列化。
>
> ⚠️ 平行前仍須確認兩者的「允許改動清單」無交集（見 CLAUDE.md 既有碼前置檢查）。

## 子任務詳細規格

### 子任務 1：{名稱}

- **狀態**：待執行 / 進行中 / 完成 / 重跑中
- **負責 Agent**：
- **本票交付什麼**（寫**使用者能完成的行為**，不是實作步驟）：
  > 例：「使用者能在列表頁點『新增』，填完表單送出後，該筆資料出現在列表上」
  > 反例（禁用）：「建立 create API 與 form 元件」← 這是實作步驟，不是交付
- **Blocked by**：無 — 可立即開始 / 子任務 N
- **垂直切片涵蓋層次**（勾選本票真的會碰到的層）：
  - [ ] 資料層（表／schema／migration）
  - [ ] 邏輯層（API／業務邏輯／腳本）
  - [ ] 介面層（頁面／元件）
  - [ ] 測試（至少一個可跑的驗收路徑）
- **允許改動的檔清單**（來自既有碼前置檢查，子 Agent 只能動這些）：
  - `src/...`
- **讀取檔案清單**（委派時傳給 agent 的完整路徑）：
  - `src/...`
  - `_管理/specs/...`
  - `_管理/常駐/領域詞彙.md`（若本票涉及領域概念）
- **任務報告檔**：`_管理/任務報告/01-{任務名}.md`（子 Agent 邊做邊寫，中斷後可自行讀回復原）
- **具體需求**（⚠️ 遵守無抽象規則：確切路徑、可執行指令、預期輸出；**不可寫「跟任務 N 類似」**）：
  （說明要做什麼，不需要貼完整程式碼，但要具體到不需要猜）
- **步驟**（每步 2–5 分鐘的單一動作）：
  1. 寫測試 `_開發檔案/tests/e2e/xxx.spec.ts` → 執行 `npx playwright test xxx` → **預期失敗**（紅）
  2. 實作 `src/...`
  3. 再執行 `npx playwright test xxx` → **預期通過**（綠）
  4. `git add <本任務檔案清單>`（**不 commit**——由主 Agent 兩關過後統一執行）
- **驗收標準**（使用者可自行確認，不需讀程式碼）：
  - [ ]
  - [ ]
- **產出檔案**（預期新增或修改）：
  - `src/...`
- **驗證證據**（完成時填，原則四強制）：實跑指令 + 輸出摘要（通過/失敗數）
  > 涉及畫面呈現時，視覺化驗證見 `CLAUDE.md`「🖼️ 視覺化優先」

## 🏁 最終全分支審查（全部子任務完成後執行一次）

> 每個子任務各自通過**不代表合起來是對的**——跨任務問題只有看完整 diff 才看得見。

- **執行日期**：
- **材料準備（主 Agent 做，reviewer 不能執行指令）**：
  - [ ] `git diff <上方「分支起點 hash」>..HEAD > _管理/任務報告/全分支diff.txt`
  - [ ] 跑全套測試，**實跑輸出**貼進委派 prompt
  - [ ] 派 reviewer **用「模式 C」**
- **檢查項目**（reviewer 全部都要看，不可只挑高風險）：
  - [ ] 介面一致性（各任務產出的型別／API 簽章是否互相吻合）
  - [ ] 無重複實作（不同任務是否各自造了功能相同的輪子）
  - [ ] 任務間邏輯無衝突
  - [ ] 規格覆蓋（對照本檔子任務清單，有無需求其實沒被實作）
  - [ ] 測試結果（**引用主 Agent 提供的實跑輸出**；未提供則回報「缺測試輸出，無法確認」）
- **結果**：通過 / 有問題（列出並處理）
