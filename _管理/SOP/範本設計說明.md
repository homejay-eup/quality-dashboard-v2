# SOP／範本設計說明（為什麼這樣設計）

> 這份是**給要改範本的人**看的——`CLAUDE.md` 各條規則背後的理由與取捨。
> AI 日常執行任務**不需要讀這份**；`CLAUDE.md` 已含所有可執行規則。
> 改 `CLAUDE.md` 的規則前，先看這裡對應段落，確認沒有推翻某個刻意的取捨。

---

## 派工顆粒度：為什麼「一次派工＝一個任務」

一次派工做多個任務時，子 Agent 的 context 會愈做愈肥，後面的任務被前面任務的雜訊污染，且壞掉時無法定位是哪個任務造成的。所以每個任務都是一次獨立的 fresh-context 派工，prompt 只帶「這一個任務」需要的東西，不貼 session 累積歷史。

## commit 責任分工：為什麼子 Agent 只 stage 不 commit

早期設計是「子 Agent 自行 commit」，優點是「誰改的誰指定檔案清單」。但代價是未過審的版本進了 git 歷史，只能用 `revert` 洗，反覆修正會累積一串壞 commit。

改為「子 Agent 只 `git add <明確清單>`、主 Agent 兩關過後統一 commit」後：staging area 跨派工持續有效（共用同一工作樹與 `.git`），所以「檔案清單由改的人指定」的優點完整保留，而「壞版本進歷史」的代價消失。reviewer 判 🔴 時尚未 commit，回派修正即可。

## 原則四：為什麼要上 hook（而非只靠 prompt）

原則四是唯一被稱為「使用者品質防線」卻曾 100% 依賴自我申報的機制，而自我申報不可靠（某次改版自己就用了 9 次「半修」示範）。所以加了技術層閘門。

四條設計原則：
1. **只擋「沒跑過」不擋「跑了但沒過」**——判斷通過與否需解析各棧輸出，脆弱易誤擋，交給 prompt 規則。
2. **依 staged 內容判斷**——純文件/設定 commit 天然放行，不需特例。
3. **fail-open**——腳本出錯/非 git repo/無法解析 → 一律放行。教訓來自 RTK hook 未安裝時擋掉所有 Bash 的事故。
4. **`[skip-verify]` 逃生門 + 留痕**，且只有使用者可指示。

`[skip-verify]` 只認**指令第一行**：舊版比對整條指令字串，導致 commit message 內文只要「提到」這個 token（例如 changelog 描述逃生門）就被當成使用逃生門而靜默放行未驗證的程式碼。文件提到這個 token 時一律用反引號包起來。

### 為什麼驗證失敗時連 `git add` 都不做

閘門 hook 只記錄「驗證指令跑過了」，**不判斷有沒有通過**（判斷通過與否要解析各技術棧的輸出，脆弱易誤擋）。所以一個失敗的 build 一樣會寫下驗證標記——子 Agent 若照樣 `git add`，主 Agent 統一 commit 時閘門不會擋，壞碼直接進 repo。因此失敗時連 stage 都不做，把「成敗判斷」留在人（子 Agent 看輸出）身上。

### 為什麼禁用 `git commit -am`

`-a` 會在 commit 當下才暫存已追蹤檔的修改，PreToolUse 判斷時 index 還是空的 → 完全繞過閘門。且 `-am` 會把未經審視的工作區變更一併帶入。被擋下時的正解是重跑驗證，不是換 `-am`。

## ad-hoc 派工：為什麼保護較弱

ad-hoc（不建 agent 檔的任務型派工）繼承主 Agent 的全部工具權限，沒有 frontmatter 的 `tools:` 技術層限制，只能靠 prompt 約束＝退回靠自律。所以涉及紅線類別（安全性/schema/部署/金流）時寧可花五分鐘建角色檔。此處的安全性範圍比紅線項 1（架構層級）廣，不因未達架構層級而放寬。

## 開案為什麼要重開 session

MCP server 與 CodeGraph 索引都在 **session 啟動時**載入。開案流程是「先寫 `.mcp.json` → 再建索引」，兩者在當前 session 內都不生效。若不重開就接著開發第一個功能，既有碼前置檢查會查不到 call/import graph 而靜默降級成 Grep——原則一在專案最初期形同不存在，且沒有錯誤訊息。

## Context 門檻 10 怎麼校準

原始門檻 2 是基於 20 萬 token 容量估算；容量擴大為 100 萬（5 倍）後等比例調整為 10。但這只是概算：啟動時讀 `CLAUDE.md`／agent 定義／專案檔案的開銷是相對固定的 token 量，不隨容量等比放大，容量越大這部分佔比越小，實際可能撐得比 10 個任務更多。建議先用 10 一陣子，觀察 context 指示器實際到 70% 時大概做了幾個任務，再依實測微調。容量若再變動：新門檻 ≈ 舊門檻 ×（新容量／舊容量）。

## 分支起點 hash 為什麼必填

大型任務 Session A 開分支時要記 `git rev-parse HEAD` 到 `任務分解.md`。沒有這個值，最終全分支審查的 `git diff <分支起點>..HEAD` 無從組出；若誤用 `main..HEAD` 而剛好在 main 上做，會得到空 diff → reviewer 回報「🟢 可合併」→ 整道關卡靜默通過。

## 為什麼不設 architect agent

技術選型與架構討論由主 Agent 在腦力激盪階段直接承擔——這是產品層決策，需要與使用者往返，不適合下放給無法對話的子 Agent。

## 為什麼 CHANGELOG 被移除

範本演進歷史原本記在 `CHANGELOG.md`，但那與 git commit message 是同一件事的兩份記錄，且 commit message 能寫得更完整。現在只靠 git；v3.19 以前的內容仍可 `git show <舊 commit>:CHANGELOG.md` 取回。
