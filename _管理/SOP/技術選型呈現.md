# SOP／技術選型呈現

> 觸發時機：技術決策偏離推薦棧、或使用者有疑慮時，依此格式呈現。**是否觸發、要不要問使用者**的規則見 `CLAUDE.md`「決策分級判準」。
> **十六維度的名稱、定義、分類、適用門檻、範例，以及呈現格式，全部以本檔為唯一來源**（`CLAUDE.md` 只指過來、不重述）。

## 預設路徑（多數綠地小專案）

> **推薦棧**＝Claude 依專案類型給的主流預設組合（如 Web 應用用 Next.js + Supabase）。有疑慮就當作「偏離」處理。

開案採用推薦棧 → 十六維度免逐項填，`_管理/開案確認.md` 記一句「採用推薦棧 X，未逐項評估」即可。
只有**偏離推薦棧**、或**使用者對某項有疑慮**時，才對該決策跑下方三層格式。

## 十六維度定義

| 維度 | 定義（怎麼判斷） |
|---|---|
| 開發成本／費用 | 一次性建置成本、每月訂閱、依用量計費等，選這個要花多少錢 |
| 上市速度 | 選這個能不能快點把東西做出來驗證想法，還是光架設環境就要耗掉很多時間 |
| 同時使用人數／資料量 | 使用者變多、資料變大時撐不撐得住，會不會需要整套重寫 |
| 呈現效果／使用者體驗 | 能不能做出你要的畫面與互動效果，有沒有現成限制 |
| 速度／效能 | 使用者實際感受到的載入與回應快慢 |
| 維護與接手難度 | 之後你自己回頭改、或找人接手好不好上手；文件教學資源多不多 |
| 穩定性／成熟度 | 這個技術/服務會不會突然停止維護、版本大改壞掉舊功能、或服務商倒閉 |
| 升級與淘汰風險 | 更新頻率高不高，會不會常被迫花時間跟著改 |
| 與現有技能的契合度 | 你或未來的人熟不熟這個技術，額外學習成本高不高 |
| 供應商／社群趨勢 | 現在是成長中還是漸漸式微，長期會不會變孤兒技術 |
| 綁定風險（Lock-in）| 之後想換掉，資料搬不搬得出來，換掉代價多大 |
| 安全性與法規 | 有沒有處理個資/金流，這個技術本身有沒有現成的安全保障或符合法規 |
| 與其他必要服務的相容性 | 跟你之後要接的金流、登入、通知、分析工具搭不搭 |
| 授權條款風險 | 開源工具商業使用有沒有限制（如要求你也開源、或禁止特定商業用途）|
| 在地化支援 | 對目標市場的語言、在地金流、資料落地法規的支援程度 |
| 未來功能擴充彈性 | 三個月後想加新功能時，這個架構會不會擋路 |

## 十六維度分類與範例

| 類別 | 維度 |
|---|---|
| 現在的成本 | ①開發成本／費用　②上市速度 |
| 規模與體驗 | ③同時使用人數／資料量　④呈現效果／使用者體驗　⑤速度／效能 |
| 長期維運 | ⑥維護與接手難度　⑦穩定性／成熟度　⑧升級與淘汰風險　⑨與現有技能的契合度　⑩供應商／社群趨勢 |
| 風險與退場成本 | ⑪綁定風險（Lock-in）　⑫安全性與法規　⑬與其他必要服務的相容性　⑭授權條款風險 |
| 產品/市場特性 | ⑮在地化支援　⑯未來功能擴充彈性 |

> ⚠️ **適用範圍**：僅限技術棧／框架／核心第三方服務層級的選型，且不易逆轉（換掉需改動多處呼叫端，或需要資料遷移）。單一函式的內部寫法、元件內部命名、不影響上述維度的重構不算。
> 例：換資料庫、導入 Redis ＝算；表單欄位加 debounce、函式拆兩個 ＝不算。

## 維度適用性標記（觸發完整格式時才做）

逐一過一遍十六維度，明顯不適用的標記「不適用（原因：___）」而非跳過不填——**十六維度清單本身不因專案性質而增減**，只在填寫時標記適用性，避免情境變化後清單裡完全找不到這一項、沒人想到要補回來。

> **範例**：可複用的 base/kit 專案（非終端產品，如共用元件庫、底座工具）通常「上市速度」「同時使用人數」可標不適用；但「綁定風險」「授權條款風險」對 base kit 反而影響更廣（風險會被所有下游複用的專案繼承並放大），**不建議標不適用**。

## 「架構決策」的定義、門檻與範例

**定義**：會影響系統整體結構、且事後要改代價很高（牽動大量既有程式碼）的技術性決定。

要不要拆微服務/單體、要不要換掉核心資料庫、要不要重新設計權限模型架構＝算；單一 API route 內部要不要拆函式、換個不影響十六維度任一項的內部工具函式庫＝不算。

## 呈現格式（三層）

### 第一層：完整比較表
| 維度 | 選項 A | 選項 B |
|---|---|---|
| （十六項逐一填）| | |

### 第二層：這次決策的關鍵差異
> 只挑兩個選項差異有實質影響的 3–5 項

### 第三層：AI 建議
> 附建議選項＋理由，理由須對應第二層列出的維度，不可用「比較靈活」等無法對應具體維度的說法
