# SOP／大型任務

> 主 `CLAUDE.md` 只在「觸發時」指你來讀這份。平常不載入，省 context。
> 收錄兩件不常用、但需要時很重要的流程：大型任務的 Session 拆分執行、Git Rollback。

> ⚠️ **觸發條件不在本檔**——單一來源是 `CLAUDE.md` 的「Context 預算規則」。
> 本檔只講「**已判定要分解之後怎麼做**」，不重複判斷標準（避免規則多處分歧）。

---

## 一、大型任務的 Session 拆分執行

**前提**：已依 `CLAUDE.md` Context 預算規則判定本任務需要分解。

**核心紀律**：主 Agent ＝ **薄協調者**——只讀管理檔，程式碼閱讀全數下放給執行 session 的 子 Agent（各自 fresh context）。Session A 分解、Session B–N 執行，context 永遠不爆。

> ⚠️ **把關密度取捨**：大型任務中間過程（任務邊界切分、既有碼前置檢查的允許改動清單）本來就由 AI 自主處理，不逐次停下確認（跟決策分級判準的紅線判斷各自獨立）。把關重心集中在**最終全分支審查**——中途減少確認換取效率，代價是問題要到全部子任務做完才會被抓到。若不能接受這個取捨，可自行要求恢復逐次確認。每個子任務仍先講一句理解的方向。

### Session A：分解（只做分解，不執行任何修改）

0. **開分支並記錄起點**（最終全分支審查需要這個值）：
   ```bash
   git checkout -b feat/{大任務名}
   git rev-parse HEAD          # 把結果寫入 任務分解.md 的「分支起點 hash」欄
   ```
   > 沒有這一步，最終全分支審查的 `git diff <分支起點>..HEAD` 無從組出來；若誤用 `main..HEAD` 而剛好在 main 上做，會得到**空 diff → reviewer 回報「🟢 可合併」→ 整道關卡靜默通過**。
1. 讀 `_管理/常駐/` 全部五檔：`此次任務.md`、`專案規格.md`、`方案紀錄.md`、`領域詞彙.md`、`踩坑記錄.md`
2. 若分解需要理解現有結構，可讀相關程式碼；**不執行任何修改**
3. **任務邊界（垂直切片方式）與優先順序皆由 AI 自主決定**，寫入 `任務分解.md` 即可，不需先問
4. 產出 `_管理/任務分解.md`：
   - **子任務必須是垂直切片**（窄但完整穿過所有層，完成後使用者能自己點開驗收）
   - 每個子任務標明 **Blocked by**（前置子任務／或「無阻擋可立即開始」）
   - **內部步驟切到 2–5 分鐘顆粒度**，且**遵守無抽象規則**（禁「TBD／跟任務 N 類似／加上驗證」等佔位語言——讀計畫的是 fresh context 子 Agent，看不到你的對話）
   - **規格覆蓋檢查**：分解完成後逐條比對規格，確認**每一條需求都對應到某個子任務**，無遺漏
   - 格式、涵蓋層次勾選、大範圍機械式改動的 **expand-contract** 例外 → 見 `_管理/範本/任務分解範本.md`
5. Session 結束，**不執行任何程式碼修改**

### Session B、C、D…：執行（每次一個子任務）

1. 讀 `任務分解.md` → 找第一個「待執行」且 **Blocked by 已滿足**的子任務
2. 走 `CLAUDE.md` 的「🚧 既有碼前置檢查」（CodeGraph 查關聯／找複用 → 宣告允許改動清單，紅線類別依決策分級判準另行確認）
3. **一次派工＝一個子任務**（fresh context）：依該子任務的「讀取檔案清單」委派對應 子 Agent（**只給它需要的檔案**），並指定其**任務報告檔** `_管理/任務報告/{編號}-{任務名}.md`（**格式見 `_管理/範本/任務報告範本.md`**，不要自創格式）
   > ⚠️ 派工 prompt **不得**貼入前序任務的累積摘要，只傳本任務直接相依的那一項（見 `CLAUDE.md`「派工顆粒度」）
4. tester 驗規格 → reviewer 審品質（**兩關都要過**）→ **範圍稽核**（`git diff --cached --name-only` vs 允許改動清單）→ **主 Agent 統一 commit**
   > **commit 責任分工的唯一來源是 `CLAUDE.md`「commit 責任分工」表**，本檔不重述時序。要點：子 Agent 只 `git add`、**不 commit**；主 Agent 兩關過後才 commit，故未過審版本不進歷史。reviewer 判 🔴 時**尚未 commit**，回派修正即可，不需要 `git revert`。
5. 更新 `任務分解.md` 標記完成（含**驗證證據實跑輸出**與範圍稽核結果）
6. 可結束 session；下個 session 從步驟 1 繼續
   > 中斷後子 Agent 可讀自己的**任務報告檔**復原，不依賴主 Agent 記憶
   > ⚠️ **子任務放棄或中止時**：先 `git reset`（保留工作區）清空 index，否則殘留的 staged 內容會混進下一個子任務的範圍稽核。

### 🏁 全部子任務完成後：最終全分支審查（一次）

⚠️ **reviewer 不能執行指令**（工具只有 Read/Grep/Glob），**材料必須由主 Agent 先產出**——完整三步見 `CLAUDE.md`「🏁 最終全分支審查」（唯一來源），摘要：

1. 主 Agent 跑 `git diff <任務分解.md 記錄的分支起點 hash>..HEAD > _管理/任務報告/全分支diff.txt`
2. 主 Agent 跑全套測試，把**實跑輸出**貼進委派 prompt
3. 派 reviewer **用「模式 C」**審查，讀上述材料 + `任務分解.md` + 各子任務報告

檢查跨任務問題（介面不一致、重複實作、邏輯衝突、規格漏實作）。**每個子任務各自通過不代表合起來是對的**。檢查清單見 `_管理/範本/任務分解範本.md` 末節。

> `全分支diff.txt` 是**暫存產物**（已列入 `.gitignore`），審查完可刪，不要 commit。

> **要平行執行時**：只有 `Blocked by` 標「無阻擋 — 可立即開始」的子任務彼此**才可**平行做，且必須確認兩者的「允許改動清單」**無交集**。有阻擋關係的一律序列化。
> ⚠️ AI 無法自行調度跨 session 並行——平行需人工開第二個 Claude Code session。若要用 git worktree 隔離，人工自行 `git worktree add` 並在新 worktree 內跑一次 `codegraph init -i`（否則原則一 blast radius 在該 worktree 失效）。範本不再內附 worktree 腳本（單人開發實務上極少用到）。

## 二、Git Rollback SOP（子 Agent 執行到一半失敗）

程式碼已改但未完成時，**不要直接重跑**，先保護現場：

```bash
git status     # 確認哪些檔案已改
git stash      # 暫存現有變更（保留，不丟棄）
```

1. 分析失敗原因，決定繼續還是重來
2. **繼續**：修正後 `git stash pop` 恢復，再繼續
3. **重來**：`git stash drop` 丟棄，進入類型 1 迭代
4. **不確定**：保留 stash，問使用者後決定

> 回滾已 commit 的變更用 `git revert <hash>`，**不用 `reset --hard`**（避免遺失歷史）。

### 已部署版本要回滾

屬部署動作 → 走紅線先問人類。用平台自身的回滾機制（Vercel Deployments、資料庫 PITR 等），不靠 git；`git revert` 只還原程式碼、不會撤回已發生的部署與資料變更。
