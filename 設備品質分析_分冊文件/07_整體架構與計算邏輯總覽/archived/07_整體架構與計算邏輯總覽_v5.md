## 1. 品質分析範圍

### 1.1 資料漏斗（期間內）

```
派工量  →  回廠量  →  維修量  →  報廢量
（cohort）  （已回廠子集） （送修子集） （報廢子集）
```

- **派工量**：期間內「品項完工日期」落在期間內的全部派工列（cohort），是所有後續計算的母體。
- **回廠量**：cohort 中實際回廠的子集。Web 版以「回廠狀態」欄位過濾（`isReturned`，見 §10.2），
  Excel／Python 版另有不同定義（見 §11 差異說明）。
- **維修量／報廐量**：回廠子集中，進一步依「完成原因」「報廢原因」判斷出的維修分類與報廢狀態，非獨立的另一張表，而是同一批回廠明細依欄位判斷出的類別。

### 1.2 產品類別

| 類別 | 範圍界定（設備類型 + 維護原因） |
|------|-------------------------------|
| 車機 | 設備類型 = 車機 ／ 維護原因 = 訊號異常 |
| 鏡頭 | 設備類型 = 鏡頭 ／ 維護原因 = 影像異常(鏡頭) |

> 「維護原因」是派工來源欄位（非本系統判斷產生），用來把 cohort 縮小到「車機分析」或「鏡頭分析」兩個分頁各自的範圍。兩個分頁各自獨立計算彙整總覽／KPI／圖表，互不影響。

### 1.3 期間定義（季度累積制）

| 期間代碼 | 涵蓋月份 |
|---------|---------|
| Q1 | 1–3 月 |
| Q2 | 1–6 月 |
| Q3 | 1–9 月 |
| Q4 | 1–12 月 |

每年從 1 月重新累積，不跨年累積（例：2026-Q2 = 2026-01 ～ 2026-06，不含 2025 年資料）。

## 4. 判斷邏輯：規則 A — 維護類型（來源欄位：維護細節）

依優先順序比對關鍵字，全無命中或維護細節空白 → 其他。

| 維護類型 | 關鍵字 |
|----------|--------|
| 失聯 | 失聯、無法連線、無法開機、無法開啟 |
| 訊號異常 | 訊號異常、訊號、補傳、大量補傳、延遲、熄火在跑、車機異常、車機NG、車機故障、觸發異常、開關機、重複開關機、重開關機、重開機 |
| 定位不良 | 定位不良、定位、定位V、AB點 |
| 酒測異常 | 酒測異常、酒測器異常、酒測故障、酒測器故障、酒測數值異常、酒測值異常、酒測值不準、酒測不準、酒測連不到、酒測無法連線 |
| 進水/模糊 | 進水、模糊、浸水 |
| 水波紋 | 水波紋 |
| 時有時無 | 時有時無 |
| AB對調 | AB對調、AB拆換 |
| 黑畫面 | 黑畫面、黑藍畫面、黑白畫面、藍畫面、白畫面、黑屏、黑頻、白屏、白頻 |
| 硬碟發報異常 | 無法錄影、硬碟發報異常 |
| 其他 | 維護細節為空白 或 無任何關鍵字命中 |

**彙整總覽只取其中 5 類**（其餘 4 類併入「其他」）：

| 設備 | 彙整總覽故障原因 5 欄（依序） |
|------|-------------------------------|
| 車機 | AB點、失聯、定位不良、訊號異常、其他 |
| 鏡頭 | 黑畫面、進水/模糊、水波紋、時有時無、其他 |

> **5 欄與回廠量的關係**：
> 第 5 欄「其他」的程式實作是**餘數欄**，計算方式固定為 `其他 = 回廠量 − 前4欄加總`
> （`metrics.js aggregate()`：`row[faultCols[faultCols.length-1]] = a.回廠量 - sum4`），
> 不是獨立分類統計出來的。
>
> - 前 4 欄（車機：AB點/失聯/定位不良/訊號異常）是回廠子集中，用「維護類型」關鍵字比對出的
>   4 種類型，**不包含**酒測異常、AB對調、硬碟發報異常，也不包含維護細節空白或無命中的列——
>   這些全部落在第 5 欄「其他」。
> - 因為「其他」是用回廠量反推出來的餘數，**「前4欄 + 其他」5 欄加總 恆等於 回廠量
>   （＝ isReturned 子集筆數）**，但這是設計上的湊數關係，**不是**「4 個具名故障原因本身就窮盡了
>   回廠量」的意思。若只加總 4 個具名故障原因（不含「其他」），得到的只是回廠量的一個子集，
>   通常會小於回廠量。
> - `isReturned` 本身的判斷依據是**回廠狀態**欄位（非「無記錄」且非「不回廠」，見 §10.2），
>   跟「故障原因／維護類型」完全無關，是兩套獨立的分類維度，跟 §7 的四桶判斷也無關。

## 6. 判斷邏輯：規則 C — QC（現行 v5，依優先序判斷）

| 優先序 | QC 值 | 條件 |
|--------|-------|------|
| 1 | 廠商檢測正常 | 維修分類 = O /測試正常 |
| 2 | 廠商完修 | 維修分類 ∈ {X /已完修、V /已完修 人為、維修換貨＋換貨條碼} |
| 3 | 廠商報廢 | 維修分類 ∈ {E /過保報廢、G /評估後退修、D /停產報廢、H /人為報廢} |
| 4 | **其他(未過)** | 維修分類 ∈ {無維修資訊、不送修} 且 報廢原因不為空白 且 已使用年限 < 該設備類型年限門檻（鏡頭 1 年／車機 3 年） |
| 5 | 回廠報廢 | 維修分類 ∈ {無維修資訊、不送修} 且 報廢原因不為空白（且不符優先序4的年限條件） |
| 6 | 回廠QC | 維修分類 = 不送修 且 報廢原因為空白 |
| 7 | 其他 | 維修分類 = 無維修資訊 且 報廢原因為空白 |

> **v5 變更重點**：「不送修 + 有報廢原因」與「無維修資訊 + 有報廢原因」套用完全相同的報廢分支判斷（2026-07-17 決議）；v4 以前「回廠其他」已改名「其他(未過)」。
>
> 注意：規則 C（QC 判斷）本身**沒有變動**——v3 調整的是下一步「§7 四桶判斷」怎麼把 QC／維修分類 結果分進良品/不良品/過保/未歸類（v3 當時還只有三桶，v8 才擴充為四桶），QC 值本身 7 種仍照上表判斷。

## 7. 四桶判斷（良品／不良品／過保／未歸類）—— 互斥且加總＝回廠量（00_規則定義.md 規則G，v8）

> **2026-07-23 使用者裁決三桶窄口徑定義（v7），2026-07-24 再裁決新增第四桶「未歸類」（v8）**：
> v7 的良品/不良品/過保三桶彼此互斥，但刻意不窮盡回廠量（H/V/其他(未過)/已遺失 不計入任何桶），
> 導致 KPI 卡片「良品+不良品+過保 ≠ 回廠量」「三個期間率加總 ≠ 100%」。使用者確認後，
> v8 新增第四桶「未歸類」收攏這些情況，四桶現在**彼此互斥且加總＝期間回廠量**。

| 桶 | 條件 |
|----|------|
| 良品 | QC ∈ {廠商檢測正常、回廠QC、其他} |
| 不良品 | **維修分類** ∈ {G /評估後退修、X /已完修、維修換貨＋換貨條碼}（不含 D/E/H/V） |
| 過保 | **維修分類** ∈ {D /停產報廢、E /過保報廢} 或 QC = 回廠報廢（不含 QC=其他(未過)） |
| 未歸類（v8 新增） | 不屬於良品／不良品／過保 的其餘情況，即：維修分類 = H /人為報廢、維修分類 = V /已完修 人為、QC = 其他(未過) |

**特例（沿用 2026-07-17 決議，v8 起明確歸入第四桶）**：回廠狀態 = 已遺失 → 良品／不良品／過保三桶皆為 false，**且未歸類強制為 true**（已遺失不等於可沿用，避免虛增再使用率；v7 時只是「不計入三桶」，v8 起明確落在未歸類，不再是隱含狀態）。

**重要：四桶（良品／不良品／過保／未歸類）互斥且加總＝期間回廠量**，四個期間率（再使用率＋期間不良率＋期間過保率＋期間未歸類率）加總恆等於 100%。

> **「未歸類」的定位**：這是收攏 H／V／其他(未過)／已遺失 四種業務意義不同情況湊成的桶
> （人為疏失／人為疏失但已修好／未過保早期報廢／設備遺失），本身**不是**一個有獨立品質意涵的
> 分類，不像良品/不良品/過保各自對應明確的品管動作。用途是讓 KPI 比率能完整對帳到 100%，
> 不是要拿來當作「有問題的品項」去追蹤或究責。
>
> **與 v7 的差異**：v7 三桶互斥但不窮盡回廠量（差額＝H+V+其他(未過)+已遺失 筆數，需要另外
> 心算才知道去了哪）；v8 把這個差額正式收成第四桶，數字上完全等價，只是多一個明確的欄位/KPI卡
> 呈現，不影響良品/不良品/過保三桶本身的判定邏輯。
>
> **與 v1/v2 的差異（沿用 v7 說明）**：v1/v2 用的是「不良品＝QC∈{廠商報廢,廠商完修,回廠報廢,其他(未過)}」（過保是不良品的子集，非互斥，良品+不良品=回廠量 恆成立，本質上是二分法，等同於 v8 的「良品 vs 不良品(全)」）。v7/v8 改成窄口徑四桶，兩種口徑分別對應冊03 30欄彙整總覽裡「回廠不良品數(全)」（v1/v2 二分邏輯）與「回廠不良品數」＋「未歸類數」（v8 四桶邏輯，見 §9.1）。

程式碼對應（`transform.js calcBuckets()`）：

```js
function calcBuckets(QC, 維修分類Code) {
  const 良品  = ['廠商檢測正常', '回廠QC', '其他'].includes(QC);
  const 不良品 = ['G /評估後退修', 'X /已完修', '維修換貨＋換貨條碼'].includes(維修分類Code);
  const 過保  = ['D /停產報廢', 'E /過保報廢'].includes(維修分類Code) || QC === '回廠報廢';
  const 未歸類 = !良品 && !不良品 && !過保;
  return { 良品, 不良品, 過保, 未歸類 };
}
```

## 8. 規則 E — 已使用年限

- **單筆公式**：`(品項完工日期 − 進貨日) / 365`，取小數點第一位；任一日期缺失或差值為負（資料異常）→ null。
- **回廠過保數判斷**（v3 修正，配合 §7 四桶定義）：符合任一條件即算回廠過保數：
  - 維修分類 = D /停產報廢
  - 維修分類 = E /過保報廢
  - QC = 回廠報廢
  - ~~QC = 其他(未過)~~ ← **v3 移除**：其他(未過) 已改為不計入任何桶（見 §7），不再算進回廠過保數
- **彙整層級「已使用年限」**：對回廠過保數明細取平均，取小數點第一位；無可用記錄 → 顯示空白。
  > v1/v2 這裡原本要「排除 QC=其他(未過)」，v3 起這個排除條件變成多餘（因為過保定義本身已經不含其他(未過)），程式碼已同步簡化。

## 10. 各項比率（KPI）計算邏輯

### 10.1 五種比率、兩種分母

KPI 共有 5 個比率指標，分成「期間率」「整體率」兩組，**分母不同**：

| 分組 | 比率 | 分子 | 分母 | 意義 |
|------|------|------|------|------|
| 期間率 | 期間再使用率 | 良品數 | 期間回廠量 | 回廠品項中，可繼續使用的比例 |
| 期間率 | 期間不良率 | 不良品數 | 期間回廠量 | 回廠品項中，判定不良的比例（窄口徑，見 §7） |
| 期間率 | 期間過保率 | 過保數 | 期間回廠量 | 回廠品項中，過保的比例（不含其他(未過)，見 §7） |
| 期間率（v8 新增） | 期間未歸類率 | 未歸類數 | 期間回廠量 | H/V/其他(未過)/已遺失 佔回廠量的比例，非核心品質指標，僅供對帳 |
| 整體率 | 整體不良率 | 不良品數 | 總線上量 | 不良品數佔全部在線設備的比例（母體更大，數值通常遠低於期間率） |
| 整體率 | 整體過保率 | 過保數 | 總線上量 | 過保數佔全部在線設備的比例 |

> **分母為 0 的處理**（`safeDiv`）：回廠量或上線量為 0 或未定義時，比率一律回傳 0（不會拋錯或顯示 NaN）。
>
> **v8 起**：良品數 + 不良品數 + 過保數 + 未歸類數 ＝ 期間回廠量（見 §7），四個期間率加總恆等於 100%。v7 之前「三者加總 ≠ 100%」的提醒已不適用。

### 10.2 KPI 卡片（Dashboard 頂部／落地頁報告）與程式欄位對照

`js/metrics.js` 的 `computeKPI()` 回傳欄位：

```js
{
  派工量, 期間回廠量, 良品數, 不良品數, 過保數, 未歸類數, 總線上量,
  再使用率,     // = 良品數 / 期間回廠量
  期間不良率,   // = 不良品數 / 期間回廠量   ← 不良品數為窄口徑（G+X+換貨）
  期間過保率,   // = 過保數   / 期間回廠量   ← 過保數不含其他(未過)
  期間未歸類率, // = 未歸類數 / 期間回廠量   ← v8 新增，H+V+其他(未過)+已遺失
  整體不良率,   // = 不良品數 / 總線上量
  整體過保率,   // = 過保數   / 總線上量
}
```

`良品數`／`不良品數`／`過保數`／`未歸類數` 四個原始計數欄位本身，會隨著 §7 `calcBuckets()` 的定義變動自動改變（`computeKPI()` 直接讀 `r.良品`／`r.不良品`／`r.過保`／`r.未歸類` 四個布林欄位加總，沒有另外複製一份判斷邏輯），因此三桶/四桶規則一落地，KPI 卡片、彙整總覽期間率（`aggregate()` 的 `不良率`／`過保率`／`未歸類率`／`再使用率`）、月趨勢圖表的「不良品數」，全部自動採用新口徑，不需要在每個檔案各自重寫規則。

| KPI 卡片 | 定義 | 程式欄位 |
|-----|------|------|
| 總線上量 | 篩選範圍內上線量加總 | `k.總線上量` |
| 期間回廠量 | isReturned 子集筆數（見 §10.3） | `k.期間回廠量` |
| 期間再使用率 | 良品數 / 期間回廠量 | `k.再使用率` |
| 期間不良率 | 不良品數 / 期間回廠量 | `k.期間不良率` |
| 期間過保率 | 過保數 / 期間回廠量 | `k.期間過保率` |
| 期間未歸類率（v8 新增） | 未歸類數 / 期間回廠量 | `k.期間未歸類率` |
| 整體不良率 | 不良品數 / 總線上量 | `k.整體不良率` |
| 整體過保率 | 過保數 / 總線上量 | `k.整體過保率` |
| 未歸類數（v8 新增，次要計數卡） | H+V+其他(未過)+已遺失 筆數 | `k.未歸類數` |

同期比較（YoY）：以上每個 KPI 各自對當期、比較期分別計算，前端顯示差值（▲/▼ 百分點或數值）。

> 「彙整總覽」表（`aggregate()`，見 §9.1）的逐 ERP品號列本身也有 `不良率`／`過保率`／`未歸類率`／`整體不良率`／`整體過保率` 等比率欄位，跟 KPI 卡片共用同一組 `r.良品`／`r.不良品`／`r.過保`／`r.未歸類` 布林值，兩處口徑保證一致。

### 10.3 isReturned／期間回廠量 定義

```js
const isReturned = (r) => r.回廠狀態 && r.回廠狀態 !== '無記錄' && r.回廠狀態 !== '不回廠';
```

- 期間回廠量＝isReturned 子集筆數，判斷依據**只看「回廠狀態」欄位**，跟「故障原因／維護類型」「四桶判斷」都無關，是三套獨立的分類維度。
- 「故障原因 5 欄」是 isReturned 子集裡再依「維護類型」分出來的（含 1 個餘數欄「其他」），
  5 欄加總會等於期間回廠量，但那是餘數欄設計出來的恆等式（詳見 §4 說明）。
